# 21. `Each`: an escape hatch for iteration

- **Status:** **Proposed.** The naming is **decided** — `Each` / `EachValue` /
  `EachKey`, mirroring `All` / `Values` / `Keys`. What remains open is how far
  the hatch spreads: the range-shaped forms, the shape interfaces, and whether
  containers carry it or only views.
- **Date:** 2026-09-24
- **Evidence:** `experiments/witness/` (`RESULTS.md` §7).
- **Relates to:** ADR `0017` (which set `Keys`/`Values`/`All` and is the naming
  this parallels), `0013` (whose erratum is the cost being escaped), `0018`
  (whose views are where the cost lives), `0019` (whose spans want the
  range-shaped hatch), `0020` (whose decision this partly de-risks).

## The problem

**Iterating through a view costs a fixed ~72 ns and six allocations, and the
library's only answer is to stop using the container.**

ADR `0020` priced it and found it affordable nearly everywhere: the overhead is
per *call* rather than per element, so it falls under 5% past n≈100 and under
1% past n≈500, and in absolute terms it is one `time.Now()`. That ruling stands.
But it leaves three shapes where the cost is the whole cost, and the API has
nothing to offer any of them:

- **An empty or tiny container in a hot loop.** 990% at n=0, 74% at n=8. A map
  of views that are usually empty is a plausible, not exotic, pattern.
- **A short-circuiting search** — `Any`, `Find`, `First`. The fixed cost is paid
  in full and the walk stops after one element. Measured at **4.5x**.
- **A tight in-memory loop that does nothing else**, where 34 ns is not lost in
  the noise of a log line or a channel send.

Today a caller in one of those positions is told to materialise with
`KeySlice()`, or — by ADR `0015` — to use a plain `[]T` and forgo the container.
Both answers leave the API rather than using it.

**What is wanted is an escape hatch: a faster, deliberately less ergonomic path
that stays inside the API**, so the fast case does not require abandoning the
type.

## The proposal

Three methods, mirroring the three iterator shapes ADR `0017` settled:

| iterator (ADR `0017`) | yields | hatch | takes |
|---|---|---|---|
| `All() iter.Seq2[K, V]` | pairs | `Each` | `func(k K, v V) bool` |
| `Values() iter.Seq[V]` | values | `EachValue` | `func(v V) bool` |
| `Keys() iter.Seq[K]` | keys | `EachKey` | `func(k K) bool` |
| `Positions() iter.Seq[P]` | positions | `EachPosition` | `func(p P) bool` |

The container drives the loop and calls the function once per element;
**returning `false` stops it.** `EachPosition` is not a fourth decision — it
follows from `Positions` the same way `EachKey` follows from `Keys`.

The plural-to-singular shift is deliberate and reads correctly at the call site:
`Keys()` yields keys, `EachKey(f)` runs `f` for each key.

### It is not a new protocol

`iter.Seq[T]` **is** `func(yield func(T) bool)`. So the hatch has exactly the
shape of the sequence it parallels, and

```go
c.EachKey(f)   ==   c.Keys()(f)
```

are the same operation written two ways. That is worth stating plainly because
it settles the semantics for free: **whatever `Keys()` guarantees, `EachKey`
guarantees** — same order, same stopping rule, same behaviour on the zero value.
There is no second contract to specify or to get wrong.

It also removes one hazard rather than adding one. CLAUDE.md's second confusing
rule is that *an iterator captures the slice header, not the contents*, which
matters because a caller can take an iterator now and range it later. **`Each`
has no such gap**: there is no value handed back, so nothing is captured and
nothing can be held. Modifying the container from inside the callback is
unsupported exactly as modifying it mid-range is, but the "bound at call time"
subtlety simply does not arise.

## What it measures

Iterating a converting view, callback not capturing (or hoisted — see below):

| n | container (no view) | view, `range Keys()` | view, `EachKey` |
|---|---|---|---|
| 0 | 3.5 ns / 0 | 75.8 ns / **6** | **3.8 ns / 0** |
| 1 | 23.9 ns / 0 | 100.1 ns / **6** | **24.8 ns / 0** |
| 8 | 36.1 ns / 0 | 129.1 ns / **6** | **43.1 ns / 0** |
| 64 | 345 ns / 0 | 565 ns / **6** | **404 ns / 0** |
| 1024 | 5.73 µs / 0 | 7.92 µs / **6** | **6.75 µs / 0** |

**The fixed per-call overhead drops from ~72 ns to ~0.6 ns and the allocations
go to zero.** Nothing is returned, so the mechanism that produces the
allocations — an `iter.Seq` crossing a dynamic call, which the compiler can then
neither inline nor stack-allocate — is never engaged.

On ADR `0020`'s parameterised container the same hatch takes 3 allocations to 0
and ~32 ns to ~1.3 ns.

**Early exit, breaking after the first of 1024 elements:**

| | | allocs |
|---|---|---|
| `range Keys()` + `break` | 101.3 ns | 6 |
| `EachKey` + `return false` | **22.3 ns** | **0** |

**4.5x**, because when the walk stops immediately the fixed cost is the entire
cost. Short-circuiting searches are the profile that gains most, and they are
common.

## Why a doc note would not do: the free alternatives all fail

This is the part that decides whether the hatch is worth API surface. A caller
who knows about the cost has four things to try without any change to the
library. **None of them reaches zero, and one is a disaster.**

At n=64, through a view:

| | | allocs | bytes |
|---|---|---|---|
| `range Keys()`, per call | 589 ns | 6 | 192 B |
| `range Keys()` with the `Seq` **hoisted** out of the loop | 565 ns | **5** | 144 B |
| `Keys()(f)` — invoking the sequence by hand | 536 ns | **4** | 152 B |
| `KeySlice()`, then range the slice | 525 ns | 1 | **1152 B** |
| `iter.Pull(Keys())` | **3831 ns** | **10** | 360 B |
| `EachKey` | **430 ns** | **0** | **0 B** |

- **Hoisting the `iter.Seq` saves one allocation of six.** The range machinery —
  loop state, loop variable, yield closure — is per *range statement*, not per
  `Keys()` call, so re-ranging a hoisted sequence pays five every time.
- **Invoking the sequence by hand saves two of six.** `Keys()(f)` skips the
  range statement entirely, which is why it does better, but `Keys()` still
  returns a closure through a dynamic call, and the nested walk inside that
  closure still allocates its own machinery. This is the closest a caller can
  get unaided, and it is still 14x the hatch's overhead at n=0 (56.5 ns / 4
  against 3.9 ns / 0).
- **Materialising is not a cheap out.** `KeySlice` trades six fixed allocations
  for one sized by n — 1152 B at n=64, 18 KiB at n=1024 — and is slower than the
  hatch at every size measured, because it copies every element.
- **`iter.Pull` is far worse than the problem.** Ten allocations and, at n=1024,
  **57.7 µs against 6.71 µs** — 8.6x — because every element crosses a coroutine
  switch. It is the right tool for interleaving two sequences and the wrong one
  for going faster.

## The caller's own closure

One allocation source survives the hatch, and it belongs to the caller:

| view, n=64 | | allocs |
|---|---|---|
| callback literal written at the call site | 421 ns | **2** |
| same closure, same capture, **one level out** of the loop | 414 ns | **0** |
| closure over a pointer to a local accumulator | 411 ns | **0** |
| method value `acc.add`, taken at the call site | 427 ns | **1** |
| same method value, bound one level out | 410 ns | **0** |
| package-level func over package-level state | 405 ns | **0** |

A literal capturing a local costs two allocations — the closure and the captured
variable — because passing it through a dynamic call makes it escape.

**The fix is to hoist the binding out of the hot loop, and nothing more.** The
captured variable may stay a local: it escapes once rather than per call, which
is what `allocs/op` measures. Package scope buys nothing over that and costs the
caller shared mutable state.

Two things the docs have to say, because neither is guessable:

- **A method value is a closure.** `acc.add` is not a free reference to a
  method; it is a closure over `&acc` built where it is written, so it allocates
  at the call site and is free one level out, exactly like a literal.
- **"One level" means outside whatever loop is hot.** A helper that builds its
  callback internally rebuilds it on every call, however far outside the helper
  the loop sits — 434 ns and 2 allocations per call. Taking the callback as a
  parameter and letting the caller own it gives 405 ns and 0.

And the cost is fixed, so it matters exactly where the hatch matters:

| n | literal at call site | hoisted |
|---|---|---|
| 0 | 20.0 ns / 2 | **4.1 ns / 0** |
| 8 | 64.2 ns / 2 | **44.1 ns / 0** |
| 64 | 430 ns / 2 | **409 ns / 0** |
| 1024 | 6.66 µs / 2 | 6.53 µs / 0 — indistinguishable |

At n=64 the gap read 10% in one full run and 5% in another, so it is "a few
percent" rather than a figure; at n=1024 the sample ranges overlap and the
difference is not resolvable.

**The un-hoisted form still beats `range Keys()` by 3.8x at n=0** (20.0 ns / 2
against 75.8 ns / 6). Hoisting collects the remainder; it is not the price of
entry, and a caller who writes the obvious thing is already most of the way
there.

**On a concrete container none of this applies**: a literal at the call site of
`MapSet.EachKey` costs 0 allocations (310 ns against 414 ns for the best view
form), because escape analysis can see the callee
and prove the closure does not outlive the call. The caller's closure escapes
for the same reason the iterator does — the dynamic call — which is the whole
finding reappearing one level up in the caller's own code.

## Call sites

**Sketch — a short-circuiting search** (ADR `0019`'s `Any` shape):

```go
// stdlib baseline
found := false
for k := range m {                       // a plain map, no view
	if pred(k) { found = true; break }
}

// today, through a view
found := false
for k := range v.Keys() {                // 6 allocations, 101.3 ns
	if pred(k) { found = true; break }
}

// with the hatch
found := false
v.EachKey(func(k string) bool {          // 0 allocations, 22.3 ns
	if pred(k) { found = true }
	return !found
})
```

The hatch is visibly worse to read: the stopping condition is inverted into the
return value, and `found` has to be threaded out through a capture instead of
falling out of a `break`. **That is the trade being offered, and it should look
like one at the call site.**

**Sketch — the pathological hot loop:**

```go
// 10_000 views, most of them empty: 990% overhead on the empty ones
for _, v := range index {
	for k := range v.Keys() { consume(k) }
}

// hoist the callback once, then nothing allocates
consumeKey := func(k string) bool { consume(k); return true }
for _, v := range index {
	v.EachKey(consumeKey)
}
```

Both belong in `callsites_test.go` as the stdlib-baseline-first diff CLAUDE.md
requires, if this is accepted.

## What it costs

**Ergonomics, deliberately.** `Each` gives up precisely what range-over-func was
introduced to provide. A callback cannot `break` to a label, `continue` an outer
loop, `return` from the enclosing function, or `defer` into its frame; stopping
early means threading a sentinel back through the `bool`, and carrying a result
out means capturing a variable. It does not compose with `slices.Collect`,
`maps.Insert`, or anything else in the stdlib that consumes an `iter.Seq`.

This is the argument for the hatch sitting **beside** `Keys`/`Values`/`All` and
never replacing them, and for the doc comments to say so in the first line.

**Surface.** Eleven new methods across the five containers, mirrored on the five
views and their internal converting implementations:

| type | iterators today | hatch |
|---|---|---|
| `MapSet[T]` | `Keys` | `EachKey` |
| `SortedSet[T]` | `Keys`, `RangeKeys` | `EachKey` (+ range form, below) |
| `Map[K, V]` | `Keys`, `Values`, `All` | `EachKey`, `EachValue`, `Each` |
| `SortedMap[K, V]` | `Keys`, `Values`, `All`, `Range`, `RangeKeys` | `EachKey`, `EachValue`, `Each` (+ range forms) |
| `Vector[T]` | `Values`, `Positions`, `All` | `EachValue`, `EachPosition`, `Each` |

Sets take `EachKey` only: a set is key-only, so it has no pair form (ADR
`0017`).

## Open: the range-shaped hatch

`Range(lo, hi)` and `RangeKeys(lo, hi)` have no obvious hatch name —
`EachInRange(lo, hi, f)` and `EachKeyInRange(lo, hi, f)` are the least-bad — and
this is exactly where the fixed cost bites hardest, because a sub-range walk is
usually short.

**ADR `0019`'s spans would supply it for free**: if `Range` returns a span
object, the span carries `Each`/`EachKey` like anything else and no new name is
needed —

```go
m.Range(lo, hi).EachKey(f)          // no new method names at all
m.EachKeyInRange(lo, hi, f)         // a new name per shape, per container
```

That looked decisive until it was measured. With `Range` called on a view
**interface** — the shape ADR `0020`'s favoured design produces, where spans and
views are the same type:

| | | allocs |
|---|---|---|
| `Range(lo,hi).Keys()`, ranged | 524 ns | 4 |
| `Range(lo,hi).EachKey(f)` | 503 ns | **1** |
| `EachKeyInRange(lo, hi, f)` | **467 ns** | **0** |

**Routing the hatch through a span costs one allocation: boxing the span.** A
span is a container plus two bounds, which is wider than one word, so it cannot
box free — and that allocation lands on the very call the hatch exists to make
free. The direct method has no span value to box and reaches zero.

So the two are not equivalent, and the choice is a real one: **one allocation
and no new names, or zero allocations and four new names.** It should be settled
with `0019` rather than here, since it depends on whether spans exist at all.

*(Measuring this required defeating devirtualization — with a single visible
implementation assigned to a local, the compiler proves the dynamic type and
every reading is 0. The harness uses two implementations behind a
runtime-selected branch. This is the third time in this line of work that a
monomorphic interface has flattered a design; it is worth a standing warning in
the experiment.)*

## What to decide

1. **The range-shaped hatch** — above. Deferred to ADR `0019`, but it is a
   genuine trade, not a formality.
2. **Whether the hatch goes on the shape interfaces.** Five of the nine in
   `contracts.go` would gain one method each (`Keys`, `Values`, `KeyValues`,
   `Positions`, `PositionValues`). Against: it widens the interfaces that exist
   to be small. For: generic code taking a shape interface is *the* place the
   dynamic call is unavoidable, so a hatch that is not on the interface is
   missing from the one context that most needs it.
3. **Whether containers carry it or only views.** On a concrete container the
   range form already fuses to zero, so a container gains nothing directly — but
   it must implement the method to satisfy any interface that declares it, and a
   caller writing generic code over a container benefits. Falls out of (2).
4. **Whether `Each` on a `Vector` is worth having at all**, given `Positions`
   and `At` already allow an index loop with no iterator.
5. **Whether this changes ADR `0020`'s decision.** It lowers the stakes: the
   6-vs-3 allocation gap between today's view and the parameterised container is
   the main performance difference between them, and the hatch gives **both** a
   zero-allocation path. It does not touch point-read dispatch (1.29 ns against
   0.37) or boxing at generic boundaries, which remain as they were.
