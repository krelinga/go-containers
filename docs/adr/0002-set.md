# 2. Set[T]: an unordered, map-backed set

- **Status:** Accepted, and implemented in `set.go`.
- **Date:** 2026-09-06
- **Evidence:** the call-site comparison below. Both versions now live in
  `callsites_test.go` and are held to identical behaviour by shared test cases.
  The receiver, interface, and `go vet` copylocks findings are tool output, not
  reasoning.

## Context

Go has no set type. The idiom is `map[K]struct{}`, which works but leaves the
concept unnamed and makes every set operation a hand-rolled loop.

Per the call-site convention, the question is not "would a Set be nice" but
**does a realistic call site get clearly shorter or safer than the `slices`/`maps`
equivalent.** Three tasks were written against the stdlib first, compiled, and
verified before any API was designed.

## Call sites

### Task A — which requested permissions are not granted? (difference)

Today:

```go
func unauthorized(granted, requested []string) []string {
	g := make(map[string]struct{}, len(granted))
	for _, p := range granted {
		g[p] = struct{}{}
	}
	var missing []string
	for _, p := range requested {
		if _, ok := g[p]; !ok {
			missing = append(missing, p)
		}
	}
	slices.Sort(missing)
	return slices.Compact(missing) // requested may contain dupes
}
```

Proposed:

```go
func unauthorized(granted, requested []string) []string {
	missing := containers.NewSet(requested...).Difference(containers.NewSet(granted...))
	return slices.Sorted(missing.All())
}
```

13 lines to 2, and the `slices.Compact` dedup step disappears because set
semantics make it free. **Clear win.**

### Task B — permissions held by both users (intersection)

Today:

```go
func shared(a, b []string) []string {
	bs := make(map[string]struct{}, len(b))
	for _, p := range b {
		bs[p] = struct{}{}
	}
	out := make(map[string]struct{})
	for _, p := range a {
		if _, ok := bs[p]; ok {
			out[p] = struct{}{}
		}
	}
	return slices.Sorted(maps.Keys(out))
}
```

Proposed:

```go
func shared(a, b []string) []string {
	return slices.Sorted(containers.NewSet(a...).Intersect(containers.NewSet(b...)).All())
}
```

9 lines to 1, and "intersection" is finally named in the code. **Clear win.**

### Task C — dedup

Today, without a map at all:

```go
func distinct(in []string) []string {
	s := slices.Clone(in)
	slices.Sort(s)
	return slices.Compact(s)
}
```

Proposed:

```go
func distinct(in []string) []string {
	return slices.Sorted(containers.NewSet(in...).All())
}
```

3 lines to 1 — but the stdlib version allocates no map and is perfectly clear.
**Not a win.** This task does not justify the container, and is recorded so we
do not later cite dedup as motivation.

### The call sites do not distinguish pointer from value

All three were written twice, once against a value `Set[T]` and once against
`*Set[T]`. **They are character-for-character identical**: the pointer is
absorbed by the constructor and the method set. The pointer/value decision below
therefore carries no call-site cost and was made purely on its other properties.

## Decision

Build `Set[T comparable]`, unordered and map-backed, **justified by set algebra
and not by membership or dedup.**

### 1. Unordered, map-backed, `comparable`

The cheapest test of whether a container wrapper earns its place. A sorted
variant is a separate question with separate costs and gets its own ADR.

### 2. Uniform pointer receivers; the zero value stays usable

Every method takes a pointer receiver, reads included. `NewSet[T](vs ...T) *Set[T]`
is a **convenience for variadic construction, not a requirement.**

The zero value works:

```go
var s containers.Set[int]
s.Add(10)     // compiles: s is addressable, so this is (&s).Add(10)
s.Has(10)     // true
```

Go rewrites a pointer-receiver call on an *addressable* value as a call on its
address, so lazy initialisation inside `Add` is all that is required. Reads on an
untouched zero value return `Has=false`, `Len=0`, and an empty iterator.
A composite literal (`Set[string]{}`) behaves identically.

This is precisely `bytes.Buffer`: *"the zero value for Buffer is an empty buffer
ready to use"*, every method on `*Buffer`, and `NewBuffer` returning `*Buffer`.
Zero-value usability and uniform pointer receivers are independent properties;
an earlier revision of this ADR wrongly treated all-pointer as implying a
required constructor.

Two reasons for the uniformity, in order of weight:

- **A single interface becomes possible.** With mixed receivers the compiler
  rejects the value type outright:

  ```
  Mixed[string] does not implement SetLike[string] (method Add has pointer receiver)
  ```

  Only `*Mixed[T]` ever satisfies such an interface, so a mixed-receiver design
  hands out pointers in practice while presenting as a value type. Uniform
  pointer receivers make that honest.

- **It makes `noCopy` free.** With value receivers, copy enforcement conflicts
  with value-returning algebra; with uniform pointer receivers there is no
  conflict at all. See Decision 5.

Aliasing is also more visible as a result: `*Set[T]` appears in every signature
that shares a set, saying so at the call site.

Two things to know about using it:

- **Satisfying the interface from a value needs `&s`.** `var _ SetLike[int] = &s`
  compiles; `= s` does not.
- **Prefer a `Set[T]` struct field over a `*Set[T]` field.** A value field lazily
  initialises on first write and is immediately usable. A nil pointer field
  panics on any method call. The value form is strictly better here.

#### Nil pointers panic uniformly

**No method special-cases a nil receiver, and none special-cases a nil
argument.** All nine methods — `Add`, `Remove`, `Has`, `Len`, `All`, `Clone`,
`Union`, `Intersect`, `Difference` — panic on a nil `*Set[T]` receiver with
`invalid memory address or nil pointer dereference`, and the three algebra
methods panic identically on a nil `*Set[T]` *argument*.

The argument case is stated explicitly so it is not later "fixed" into treating
nil as the empty set, which would contradict this decision.

A nil `*Set[T]` is almost always a bug, and silently reporting it as an empty
set would hide that bug at exactly the moment it matters. Consistent failure is
worth more than a convenience that only ever masks a mistake.

This costs nothing to implement — it is achieved by *omitting* nil-receiver
guards, not by adding checks. And it does **not** compromise Decision 2's zero
value, because that relies on nil-*map* semantics, which Go provides for free:
reads from a nil map return the zero value, `len` is 0, and `range` yields
nothing. The zero value never needed nil-receiver guards.

Uniform panics do not fall out for free, though. **Anything that only touches
the receiver or an argument inside a loop or a closure will skip the panic when
that loop does not run.** Three cases in this Set, all found by auditing the
implementation against this decision rather than by reading it:

- **`All()` must read `s.m` into a local before returning its closure.**

  ```go
  func (s *Set[T]) All() iter.Seq[T] {
  	m := s.m // panics here on a nil receiver, like every other method
  	return func(yield func(T) bool) { ... }
  }
  ```

  Ranging over `s.m` inside the closure defers the panic to iteration time. A
  side effect is that the iterator binds the map at call time rather than at
  iteration time — the defensible rule, and the one to document.

- **Variadic mutators must touch the receiver outside the loop.** `Remove(vs ...T)`
  implemented as a bare `for _, v := range vs { delete(s.m, v) }` never
  dereferences `s` when `vs` is empty, so `p.Remove()` on a nil `p` silently
  succeeds.

- **Algebra must evaluate its argument eagerly.** `Difference` implemented so
  that `o` is only reached inside `for v := range s.All()` never touches `o`
  when `s` is empty, so `empty.Difference(nil)` silently returns an empty set.
  Using `o.Len()` as the result's capacity hint both sizes the map and forces
  the evaluation.

The general rule for any container adopting this decision: **every method must
dereference its receiver, and every method taking a container argument must
dereference that argument, on a path that always executes.** Assert it with
tests that would fail without the guard, not by inspection.

### 3. Algebra returns a new `*Set`; cross-container algebra is a free function

`a.Union(b)`, `a.Intersect(b)`, `a.Difference(b)` return a new `*Set[T]` —
readable and chainable, at the cost of an intermediate allocation per operation.

**Algebra cannot live on an interface.** Go requires exact signature match and
has no covariant returns:

```
*Set[string] does not implement SetAlgebra[string] (wrong type for method Union)
    have Union(*Set[string]) *Set[string]
    want Union(SetAlgebra[string]) SetAlgebra[string]
```

No receiver choice gets past this; methods also cannot take type parameters.
Free functions can, so anything generic over containers is a free function:

```go
func UnionOf[T comparable](a, b SetLike[T]) *Set[T]        // concrete result
func UnionSeq[T comparable](seqs ...iter.Seq[T]) iter.Seq[T] // composes anything
```

`UnionSeq` was verified to union a `*Set`'s iterator with a plain slice's
`slices.Values` in one call. **`iter.Seq` is the cross-container interchange;**
methods are the concrete convenience. Only the methods ship initially.

### 4. Surface

`Add(...T)`, `Remove(...T)`, `Has`, `Len`, `Clone`, `All() iter.Seq[T]`, plus
`Union`, `Intersect`, `Difference`. `Add` and `Remove` are variadic, matching
`NewSet`.

An interface covering the container contract ships alongside: `Add`, `Has`,
`Len`, `All` — deliberately not algebra. `Remove` is absent only because this
ADR's original list omitted it; whether that was deliberate should be settled
when the interface is named. **The name is unresolved** — `SetLike` is a
placeholder.

### 5. A `noCopy` field, so `go vet` catches struct copies

`Set[T]` carries a zero-sized `noCopy` field with `Lock`/`Unlock` methods, which
`go vet`'s copylocks analyzer uses to flag struct copies.

Under the all-pointer design this is **free**. Every method takes and returns
`*Set[T]`, and copying a pointer is not copying the struct, so the entire API
vets clean — zero false positives. What it catches is exactly the residual
hazard: code that dereferences past the pointer.

| hazard | caught |
|---|---|
| `*foo = *bar` | yes |
| `deref := *foo` | yes |
| `append([]Set[T]{...}, *foo)` | yes |
| `m["x"] = *foo` where the map holds values | yes |
| `out := *s` inside a plausible but wrong `Clone` | yes |
| `func f(s Set[T])` — passing by value | yes |

The last two are the valuable ones: a shallow-copy `Clone` that silently shares
the map is precisely the bug this container exists to avoid, and vet rejects it
at the definition.

**The field must be declared first.** A zero-sized field in trailing position
forces padding — `noCopy` first leaves the struct at 8 bytes, `noCopy` last
doubles it to 16.

Two limits, both verified. copylocks does **not** flag a channel send
(`ch <- s`), so that copy path is unprotected. And copylocks does not run under
`go test` — see Consequences, which is the more consequential of the two.

## Rejected alternatives

- **Mixed receivers** (pointer on mutators, value on reads). Was the original
  decision. Rejected because the value type cannot satisfy any interface
  containing `Add`, and because it conflicts with `noCopy`. Note that its
  advantage — a usable zero value — was **not** the thing given up: Decision 2
  keeps it. What is given up is calling mutators on non-addressable values, and
  `NewSet` returning a pointer covers that case.
- **Value `Set[T]` with a required constructor.** Considered specifically as an
  aliasing fix and **verified not to be one**: `b := a; b.Add(x)` mutates `a`
  identically under both. The aliasing comes from the map reference inside the
  struct, not from how the struct was constructed. It also reintroduces a nil
  landmine — reads succeed, the first write panics with `assignment to entry in
  nil map`.
- **A `noCopy` field *in the value design*.** Rejected there, and there only.
  With value receivers it flags every legitimate value-returning method
  (`Union passes lock by value`, `return copies lock value`), so enforced
  no-copy and value-returning algebra are mutually exclusive. **That exclusivity
  is a property of the value design, not of `noCopy`.** Under all-pointer the
  conflict disappears entirely and `noCopy` is adopted — see Decision 5. An
  earlier revision of this ADR wrongly generalised the conflict to both designs.

## Consequences

- **Sharing is explicit but still real.** Two variables holding the same
  `*Set[T]` alias, exactly as two variables holding the same map do. The pointer
  makes it visible in every signature rather than eliminating it, and `noCopy`
  catches the dereferencing cases; neither prevents deliberate sharing, which is
  the point of a pointer. `Clone` is in the initial surface for this reason.
- **`go vet` is load-bearing, and `go test` does not run it.** copylocks is
  *not* in the high-confidence subset `go test` runs by default — that subset is
  `atomic, bool, buildtags, directive, errorsas, ifaceassert, nilfunc, printf,
  stringintconv, tests`. A shallow-copy `Clone` passes both `go test ./...` and
  `go build ./...`, and is caught only by `go vet ./...` or
  `go test -vet=all ./...`. Decision 5's guarantee holds only where one of those
  actually runs, so run one.
- **A `Set` value is usable but immovable.** Decisions 2 and 5 interact in a way
  neither states alone: the zero value works, but `noCopy` means a `Set` value
  cannot be passed to a function, returned, or placed in a slice literal —
  locals and struct fields only, `&s` everywhere else. "The zero value is
  usable" is narrower than it sounds.
- **Not safe for concurrent use.** There is no internal synchronisation; a Set
  behaves like the map it wraps, and callers coordinate. Recorded rather than
  revisited.
- **The sort tax remains.** `slices.Sorted(s.All())` appears wherever
  deterministic output is needed, because map iteration order is random. Every
  task above still ends in a sort. This is the strongest argument for a future
  sorted set and the clearest thing this ADR does *not* solve.
- **Every method panics on a nil pointer; zero values are fully usable.**
  `var s Set[string]` works throughout; `var p *Set[string]` panics on any call.
  The hazard lives only in the pointer form, which is why struct fields should
  hold `Set[T]` rather than `*Set[T]`.
- `All() iter.Seq[T]` plugs directly into `slices.Sorted` and `slices.Collect`
  with no adapter, which is where most of the call-site brevity comes from.
- Each algebra operation allocates a full intermediate set even when the result
  is iterated once. `iter.Seq`-returning variants are the escape hatch,
  deliberately not added now.
- ADR `0001` does not bite yet: this Set has no accessor returning an internal
  slice or map. It applies the moment one is added.

## Follow-ups

- Name the container-contract interface, and settle whether `Remove` belongs in it.
- **Serialization is undecided and currently silently lossy.** `json.Marshal` of
  a populated `Set` returns `{}` with a nil error, discarding every element; a
  struct field holding a Set marshals as `{}`; `json.Unmarshal` of an array into
  a Set fails. This follows from having only unexported fields and so will recur
  for *every* container in this library. It wants one ADR covering the library,
  not a patch to Set.
- A sorted set, if wanted, is a separate ADR — the sort tax above is its motivation.
- How a read-only view is expressed (deferred from ADR `0001`) stays open.
