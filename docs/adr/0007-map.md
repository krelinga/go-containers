# 7. Map[K, V]: a defined map type for generic programming

- **Status:** Accepted. Not yet implemented, so this constrains the change
  rather than describing it.
- **Date:** 2026-09-06
- **Evidence:** `experiments/dispatch/` (`RESULTS.md`)
- **Relates to:** ADR `0002` (shape rules — this ADR takes an explicit exception),
  `0003` (SortedMap), `0006` (`Elems2`).

## Context

ADR `0006` gave this library read-only genericity: anything satisfying
`Elems2[K, V]` can be iterated and counted generically. What is still missing is
**mutation** genericity — there is no way to write one function that works
against both a `map[K]V` and a `SortedMap[K, V]`.

The obstacle is that a builtin map has no methods. A defined type fixes that
without changing anything else:

```go
type Map[K comparable, V any] map[K]V
```

`Map[K, V](existing)` is a type conversion, not a copy: the wrapper aliases the
map it wraps, so adopting it costs nothing and mutations flow both ways.

## Call sites

Today the same operation must be written once per backing. Dropping entries that
fail a predicate:

```go
func pruneMap[K comparable, V any](m map[K]V, keep func(V) bool) {
	for k, v := range m {
		if !keep(v) {
			delete(m, k)   // safe: the spec permits deletion during map iteration
		}
	}
}

func pruneSorted[K cmp.Ordered, V any](m *containers.SortedMap[K, V], keep func(V) bool) {
	var drop []K
	for k, v := range m.All() {
		if !keep(v) {
			drop = append(drop, k)   // must NOT delete while iterating; see below
		}
	}
	for _, k := range drop {
		m.Delete(k)
	}
}
```

Proposed — one function for both:

```go
func prune[K comparable, V any](m containers.MutableMap[K, V], keep func(V) bool) {
	var drop []K
	for k, v := range m.All() {
		if !keep(v) {
			drop = append(drop, k)
		}
	}
	for _, k := range drop {
		m.Delete(k)
	}
}

prune(containers.Map[string, int](plain), keep)   // free conversion
prune(sorted, keep)                                // *SortedMap
```

**The win is reach, not brevity**, and it is not free: the generic version must
use the more conservative of the two iteration disciplines, so it collects keys
where `pruneMap` could delete in place. One function body replacing two, at the
cost of the map-specific shortcut. That trade is the whole proposition.

An earlier draft of this ADR used the in-place form as its example. Run against
the real `SortedMap` it visits `[0 1 3 5 7 9 0 0 0 0]` for a ten-entry map —
revisiting one key four times and never reaching four others — because `All`
binds the backing slice and `Delete` shifts elements within it. The final state
happened to be correct; the iteration was not.

## Decision

### 1. `Map[K comparable, V any] map[K]V`, with value receivers

`Get`, `Set`, `Delete`, `Len`, `All`, `Clone` — all on the value, not a pointer.
Mutation works because the map header points at the same hash table.

Value receivers are not merely adequate, they are the point: **`Map[K, V]`
satisfies interfaces as a value**, where every other container in this library
requires a pointer. Pointer receivers would buy lazy initialisation of a nil map
and lose that.

`experiments/dispatch/` confirms the wrapper is free rather than nominally free:
methods on a defined map type are inlined away entirely — `Get` 3.20 → 3.28 ns
and `Delete` 4.75 → 4.77 ns against the raw builtin.

### 2. ADR 0002's shape rules do not apply, deliberately

`0002` governs **struct-backed** containers. `Map` is a defined map type and
inherits its semantics from the builtin, which is more valuable than matching
the other containers. Each rule and why it is dropped:

- **`noCopy`** is impossible — there is no struct to declare it in — and also
  unnecessary. `0002` guards against a struct copy that *looks* like a value copy
  while sharing a map underneath. `Map` has no such illusion: it *is* the map, and
  every Go programmer already expects `b := a` on a map to alias.
- **Uniform pointer receivers** would defeat decision 1.
- **A usable zero value** is not available. `var m Map[K, V]` reads correctly —
  `Len` is 0, `Get` misses, `All` yields nothing — and **panics on write** with
  `assignment to entry in nil map`. This is precisely what a plain `map[K]V`
  does, and it cannot be fixed without pointer receivers.
- **Uniform nil panics** likewise do not transfer: reads on a nil `Map` succeed
  because reads on a nil map succeed.

The principle: **where a container is a thin naming of a builtin, it matches the
builtin's semantics rather than this library's conventions.** A caller who knows
Go maps already knows how `Map` behaves, and that is worth more than internal
consistency.

### 3. `MutableMap[K, V]`, the shared mutation contract

```go
type MutableMap[K comparable, V any] interface {
	Elems2[K, V]
	Get(K) (V, bool)
	Set(K, V)
	Delete(K)
}
```

Satisfied by `Map[K, V]` as a value and `*SortedMap[K, V]` as a pointer.

Deliberately minimal: only what both types genuinely share. It excludes ordered
operations, which a plain map cannot provide, and excludes anything returning
the container type, which Go's lack of covariant returns forbids on an interface
— the ceiling ADR `0002` documented for set algebra. `Clone` is excluded for that
reason, so generic code cannot copy.

**Mutation during iteration is not supported**, and the contract says so
explicitly. The two implementations genuinely differ here: the Go spec permits
deleting from a map while ranging over it, while `SortedMap.All` binds the
backing slice and `Delete` shifts within it, so the same code corrupts the
iteration. The contract takes the stricter guarantee, because `SortedMap` cannot
offer the weaker one without copying its backing on every `All`.

Iterator *binding* — whether an iterator reflects writes made after it was
created — is separately **unspecified** by this contract, and `Elems2` should say
so. `SortedMap` binds at call time, but only as a side effect of ADR `0002`'s
rule that a nil receiver must panic at the call rather than at iteration; `Map`
has a value receiver and no such problem to solve. The Go spec leaves the
question open for maps too, so "unspecified" is satisfiable by both, and
implementations offering something stronger are free to.

### 4. `SortedMap.Delete` drops its `bool`

Both become `Delete(K)`. This is a **breaking change** to `SortedMap`.

The alternative was giving `Map.Delete` the reporting signature, which requires a
lookup the builtin `delete` does not perform. `experiments/dispatch/` priced it:
**+62% on every `Map` delete**, and additive with dispatch rather than absorbed
by it — the same +2.7 ns whether called directly or through an interface, making
it roughly **4x the cost of the genericity itself** (~0.7 ns).

Taxing the free-wrapper type to preserve a return value costs more than the
information is worth. `Get` answers "was it there" for callers who need it.

**The premise deserves stating:** this breaks a shipped signature on the strength
of a microbenchmark, without establishing that `Delete` is hot in any real
workload. The measurement says the cost is 4x the genericity, not that either is
large in absolute terms. What makes it acceptable is that nothing outside this
repository depends on `SortedMap` yet, so the change is cheap now and will not be
later.

The honest cost: `SortedMap`'s binary search already knows the answer, so this
discards information that was free *there* to avoid buying it expensively
*here*. Recorded so the trade is visible rather than assumed.

## Consequences

- **The interface asymmetry is permanent.** `f(myMap)` but `f(&mySortedMap)`,
  because value receivers satisfy from a value and pointer receivers do not.
  Inherent to Go, not a defect to be fixed later.
- **`Map` serializes where its key type allows it; the other containers never
  do.** `json.Marshal` of a `Map` with string or integer keys produces real JSON
  and unmarshals back, including as a struct field, because it *is* a map. A
  struct-keyed `Map` fails outright — `json: unsupported type` — since
  `encoding/json` cannot express such keys, and `K comparable` permits them. The
  struct-backed containers marshal to `{}` with a nil error regardless of key
  type. So the library is now inconsistent under `encoding/json` in two
  directions at once, which is worse than being uniformly broken and raises the
  priority of the library-wide serialization decision.
- **A `Map` can be mutated behind your back** by anything still holding the
  underlying `map[K]V`. That is map semantics, and the free conversion is what
  makes it likely. Callers wanting isolation use `Clone`.
- **Writing to a zero-value `Map` panics.** Loud and immediate, and identical to
  a plain map, but it differs from every other container here.
- Adding a container that is a thin naming of a builtin is now a recognised
  shape, with `0002` scoped to struct-backed types rather than all containers.

## Rejected alternatives

- **Pointer receivers on `Map`.** Would allow lazy initialisation of a nil map,
  restoring ADR `0002`'s usable zero value. Rejected because `*Map[K, V]` rather
  than `Map[K, V]` would then be what satisfies the interfaces, discarding the
  one property that makes this type worth having, and because a pointer to a map
  is an unusual thing to ask callers to carry.
- **Giving `Map.Delete` the reporting signature** to match `SortedMap`. Priced at
  +62% per delete in `experiments/dispatch/`, additive with dispatch rather than
  absorbed by it. Rejected: the type's proposition is being free.
- **Both signatures on `Map`** — a quiet `Delete(K)` plus a reporting variant
  under another name, with the contract using the cheap one. Rejected as surface
  for its own sake: `Get` already answers the question, and a second name for a
  two-line composition is not worth teaching.
- **Shipping `Map` without the contract**, letting an interface emerge from a
  third implementation. Rejected because the contract *is* the motivation; a
  `Map` with methods nobody calls generically has no reason to exist, since
  `m[k]` already works.
- **Requiring the contract to permit mutation during iteration**, matching plain
  maps. Rejected because `SortedMap` cannot honour it without copying its backing
  slice on every `All`, which would tax every iteration to serve a minority of
  callers.

## Follow-ups

- Name the mutating set contract, still `SetLike`, now that `MutableMap` sets a
  precedent for the naming scheme.
- Whether a `Slice[T] []T` deserves the same treatment for ordered sequences.
- The library-wide serialization decision, now more urgent: one container is
  partly correct, three are uniformly wrong, and the inconsistency is visible to
  callers.
- Add the iteration-discipline note to `Elems2`'s doc comment when this lands.
