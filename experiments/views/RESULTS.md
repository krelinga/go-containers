# Shapes a read-only view can take

From `bench.txt`, generated by `./run.sh` (`-count=8 -benchtime=100ms`).
Provenance in that file's header; a QEMU guest, so **ratios are the durable
result**. Zero-cost baseline `BenchmarkNoOp` = 0.29 ns.

## 1. What a read-only handle prevents, and what it does not

Handing out a bare contract interface prevents nothing:

```
bare contract, type assert to container:  SUCCEEDED (Len now 2)
view, type assert to container:           false
```

`*Dict[K, V]` structurally satisfies the read contract, so a holder asserts back
and mutates. A view whose dynamic type is the view struct blocks that.

The remaining escape hatches are **tiers, not equivalents**:

| path | outcome | visibility |
|---|---|---|
| type assertion to the container | blocked by a view | invisible — looks like normal code |
| `reflect` read of the unexported field | succeeds | needs `reflect` |
| `reflect` **write** through it | **blocked by reflect itself** | — |
| `reflect` + `unsafe` | succeeds | requires importing `unsafe` |

Plain reflection cannot mutate: `reflect.Value.Interface` refuses values obtained
from unexported fields. Reaching the container needs `unsafe`, which is
greppable, lintable and conventionally reviewed. So a view moves the bar from
*invisible* to *auditable*, not from *possible* to *impossible*.

**A view is forgettable, not defeatable.** Containers must satisfy `Elems2` for
the sized constructors, so they satisfy the read contracts too, and a provider
can always pass the container directly. The seal engages only where someone
remembered it — unlike `noCopy`, which vet applies everywhere automatically.

## 2. A shallow view does not stop element mutation

```
shallow view: element mutated through it?  true (Name="MUTATED")
```

For `V = *Item`, a view blocks mutating the container but not the elements it
hands back. This is what puts projection on the table.

## 3. The four shapes

| | size | `Get` | boxing into a contract |
|---|---|---|---|
| direct container call | — | 4.44 ns | — |
| **shallow** (concrete pointer) | **8 B** | **4.38 ns** | **0.38 ns, 0 allocs** |
| **per-contract** (interface field) | 16 B | 4.82 ns | 12.16 ns, **1 alloc** |
| **projecting, field-held func** | 16 B | 5.94 ns | 12.13 ns, **1 alloc** |
| **projecting, type-param witness** | **8 B** | 5.78 ns | **0.39 ns, 0 allocs** |
| witness with an identity converter | 8 B | 5.72 ns | 0 allocs |

Three things fall out.

**Pointer-shaped or not is the whole allocation story.** A struct holding one
pointer boxes into an interface for free; one holding an interface or a func
value does not, and costs an allocation every time it is passed as a contract —
which is the common case.

**Shallow is indistinguishable from calling the container.** 4.38 ns against
4.44 ns; the forwarding method inlines away entirely.

**Projection costs ~1.4 ns regardless of how it is carried.** Field-held 5.94 ns,
witness 5.78 ns. Hoisting the converter into a type parameter buys the width and
the allocation, **not** the call. An identity witness costs the same 5.72 ns, so
unifying shallow and projecting under one type is not free.

## 4. The witness costs type arguments; aliases recover them

`WitnessView[K, V, R, C]` needs four type arguments, and `R` and `C` appear in no
argument, so inference cannot help. Aliases fix it:

```go
// generic alias, partially applied -- the shallow case
type WitnessShallow[K cmp.Ordered, V any] = WitnessView[K, V, V, idConv[V]]

// a method may return it: no new type parameter is introduced
func (d *Dict[K, V]) WitnessView() WitnessShallow[K, V]

// fully instantiated, naming a projecting view once
type ItemDictView = WitnessView[string, *Item, ItemView, itemConv]
```

Verified: `d.WitnessView()` takes no type arguments at the call site, both forms
stay 8 bytes, and **alias and long form are interchangeable in both directions**
— aliases are identical types, not distinct ones.

Two constraints the witness carries permanently:

- **Converters must be stateless**, since the view materialises the zero value.
  No configurable projection, ever.
- **Projection is not a snapshot.** `ItemView` wraps the same `*Item`, so
  `Name()` still reports `"MUTATED"`. It denies writes *through the view*; it
  does not freeze the element.

## 5. Context from earlier experiments

View costs are small, and they are worth reading against what they replace.

| measurement | source |
|---|---|
| defensive copy floor ~10 ns, then ~0.3–1 ns per element | `copycost` |
| a copying accessor called n times is O(n²) — **36 800x** a view at n=16 384, 2.1 GB in one pass | `copycost` |
| retained pointer-ful copies re-scanned every GC cycle, 2.4x cycle cost | `copycost` |
| interface dispatch +0.72 ns; generic type parameters indistinguishable | `dispatch` |
| a method wrapper over a builtin inlines away entirely | `dispatch`, `hashdict` |
| map `Get` 3.2–3.4 ns, so a view adds ~30–45% to a lookup-shaped operation | `hashdict` |

The scale worth holding onto: **projection costs ~1.4 ns per access; the copying
alternative ADR 0001 rejected costs 10 ns minimum and degrades quadratically.**

## Conclusions

Durable:

1. A bare contract interface prevents nothing; a view struct blocks type
   assertion. Neither stops `reflect` + `unsafe`, and plain `reflect` cannot
   mutate at all.
2. Views are forgettable rather than defeatable: containers satisfy the read
   contracts inherently, so sealing depends on the provider applying it.
3. Pointer-shaped views box for free; views holding an interface or a func value
   cost an allocation each time they are passed as a contract.
4. A shallow view is free. Projection costs ~1.4 ns however it is carried.
5. A type-parameter witness keeps the view pointer-shaped but requires four type
   arguments, which generic and instantiated aliases fully recover.

Perishable: every absolute number above.
