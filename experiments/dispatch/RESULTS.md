# What generic dispatch costs, and what it does not absorb

From `bench.txt`, generated by `./run.sh` (`-count=10 -benchtime=200ms`).
Provenance in that file's header; a QEMU guest, so **absolutes are soft and
ratios are the durable result** — see the note on variance below.

Zero-cost baseline: `BenchmarkNoOp` = 0.24 ns, well under the smallest
measurement here, so harness overhead is not in these numbers.

## The three call paths

| operation | raw builtin | direct method | interface value | generic type param |
|---|---|---|---|---|
| `Get` | 3.20 ns | 3.28 ns | 4.00 ns | 4.02 ns |
| `Set` | 5.09 ns | 5.02 ns | 5.54 ns | — |
| `Delete` (quiet) | 4.75 ns | 4.77 ns | 5.50 ns | 5.37 ns |
| `Delete` (reporting) | — | 7.71 ns | 8.16 ns | 8.24 ns |

## 1. A method wrapper over a builtin is free

`Get` 3.20 → 3.28 ns, `Set` 5.09 → 5.02 ns, `Delete` 4.75 → 4.77 ns. The
compiler inlines the method away, so defining methods on a defined map type
costs nothing over using the builtin directly.

## 2. Dispatch costs well under a nanosecond

Interface: **+0.72 ns** on `Get`, **+0.52 ns** on `Set`, **+0.73 ns** on
`Delete`. Generic type parameters land within noise of interface values, which
matches Go's dictionary-based stenciling for pointer-shaped types like maps.

As a share it is 8–23%, largest on the cheapest operation, because the map
operation itself dominates.

## 3. Dispatch does not absorb an extra lookup

The reporting `Delete` needs a lookup the builtin `delete` does not perform. It
costs **+2.94 ns direct (+62%)**, and **the same +2.66 ns through an interface**
— it is additive on top of dispatch, not hidden by it.

So the extra lookup is roughly **4x the cost of the genericity** it might have
been assumed to disappear into.

## A note on variance

An earlier run of the same benchmarks on this machine measured the quiet delete
at 7.89 ns and the reporting delete at 12.48 ns — absolute values well above
those above, from a slower baseline rather than a different effect. The
*proportion* was stable across both runs (+58% then +62%), as was the dispatch
overhead (~0.6–0.75 ns).

Treat the percentages as the finding and the nanoseconds as indicative. On this
hardware the lookup is 4–8x the dispatch cost depending on the run; it is never
close to free, and dispatch is never the dominant term.

## Conclusions

Durable:

1. Methods on a defined map type are inlined and cost nothing over the builtin.
2. Interface and generic dispatch cost under a nanosecond per call, 8–23% of
   these operations, with generics and interfaces indistinguishable.
3. An extra map lookup costs several times the dispatch and is additive with it.
   Genericity does not pay for API decisions made inside the callee.

Perishable: every absolute number above.

**Do not justify a more expensive method signature on the grounds that generic
code pays for dispatch anyway.** It does, and the amount is small.
