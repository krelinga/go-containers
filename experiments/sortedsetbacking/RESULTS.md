# Should a sorted set be built on SortedMap[T, struct{}]?

From `bench.txt`, generated by `./run.sh` (`-count=10 -benchtime=100ms`).
Provenance in that file's header; a QEMU guest, so **ratios are the durable
result**.

Three backings: a bare `[]T`; an entry slice laid out as SortedMap does today
(`{k K; v V}`); and the same fields reordered (`{v V; k K}`).

## 1. Today's field order costs exactly 2x, and the fix is free

| | `int` key | `string` key |
|---|---|---|
| bare | 8 B | 16 B |
| `{k K; v struct{}}` — today | **16 B** | **24 B** |
| `{v struct{}; k K}` — reordered | 8 B | 16 B |
| `{k int; v string}` vs reordered | 24 B both ways | — |

Go pads a struct whose final field is zero-sized. Building n entries confirms it
end to end — memory and time both double, and reordering recovers all of it:

| n | bare | reordered | today |
|---|---|---|---|
| 1 024 | 8 192 B / 91 µs | 8 192 B / 100 µs | **16 384 B / 154 µs** |
| 262 144 | 2 097 152 B / 3.30 s | 2 097 152 B / 3.33 s | **4 194 304 B / 6.54 s** |

**Reordering `sortedEntry`'s fields costs nothing for a normal value type and
removes the penalty entirely.** This is the same rule that decides where
`noCopy` must be declared (ADR 0002, decision 5).

## 2. The lookup gap is the comparator, not the layout

| n | bare, `slices.BinarySearch` | entry, `BinarySearchFunc` |
|---|---|---|
| 1 024 | 4.3 ns | 15.1 ns |
| 262 144 | 7.5 ns | 25.5 ns |

Reordered and today's layout are indistinguishable here, so padding is not the
cause. Searching a **bare `[]int` through a comparator closure** isolates it:

| n | `slices.BinarySearch` | `slices.BinarySearchFunc` |
|---|---|---|
| 1 024 | 4.3 ns | 15.1 ns |
| 262 144 | 7.5 ns | 25.2 ns |

Identical to the entry slices. **The ~3.4x is entirely the per-comparison
closure call.** A set over `[]T` can call `slices.BinarySearch` directly because
`T` is already `cmp.Ordered`; anything storing entries cannot.

## 3. The delegation adapter is free

Iterating 262 144 elements:

| | ns |
|---|---|
| raw `for range` over the slice | 50 687 |
| through an `iter.Seq[T]` closure | 295 132 |
| through `iter.Seq2` + a key-only adapter | 298 695 |

Wrapping `SortedMap.All()` to discard values costs **~1%, within noise**. The
6x is the iterator abstraction itself, and both designs pay it equally, since a
custom set would still return `iter.Seq[T]`.

## Conclusions

Durable:

1. `SortedMap[T, struct{}]` costs 2x memory and 2x insert time **only** because
   of field order. Reordering `sortedEntry` fixes it at no cost to normal maps.
2. The ~3.4x lookup penalty is comparator indirection, not layout, and cannot be
   removed while the backing stores entries.
3. Delegating iteration through an `iter.Seq2` adapter is free.
4. The iterator abstraction costs ~6x versus raw ranging, but is unavoidable in
   either design.

Perishable: every absolute number above.

**A SortedMap-backed sorted set is viable and nearly free once the fields are
reordered — except on lookup, where it gives up ~3.4x that a custom `[]T` keeps.**

## Aside worth its own investigation

Finding 2 applies to `SortedMap` itself: its `Get`, `Floor`, `Ceil` and `Range`
all pay the same closure per comparison. Storing parallel `keys []K` and
`vals []V` slices would let it call `slices.BinarySearch(m.keys, k)` directly and
recover the 3.4x — at the cost of splitting locality for entry iteration. That is
a change to an existing container and wants its own experiment.
