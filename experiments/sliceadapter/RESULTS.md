# What a defined slice type can and cannot do

From `bench.txt`, generated by `./run.sh` (`-count=10 -benchtime=200ms`).
Provenance in that file's header; a QEMU guest, so **ratios are the durable
result**. Zero-cost baseline `BenchmarkNoOp` = 0.22 ns. Sequences are 1024
elements.

## 1. The wall in the Map analogy: a value receiver cannot grow a slice

```
Set through a value receiver sticks=true; Append through one sticks=false
conversion from []T aliases=true, and converts back=true
```

`Map`'s `Set` and `Delete` work on a value receiver because a map header points
at shared state — mutating through any copy is visible through all of them. A
slice's **length lives in the header**, which is the value, so `append` through a
value receiver updates a copy and is discarded.

Writing an existing element does stick, because that goes through the shared
backing array. So the line is exact: **a slice adapter can read and can write in
place, but cannot change its own length.** It is not the mutable equivalent of
`Map`, and no receiver choice makes it one without giving up the value semantics
that make it an adapter.

## 2. It does not fix what `Vector` exists for

```
appends off a shared adapter header still alias=true
```

Naming a slice type changes nothing about slice semantics. All three hazards ADR
`0015` records — aliased appends, appends lost in a callee, holders splitting at
a reallocation — survive intact. **An adapter is an ergonomic convenience, not a
safety one**, which is the same thing ADR `0009` says about `Map`.

## 3. It keeps bounds-check elimination, where a struct wrapper loses it

| indexed sum of 1024 | | vs raw |
|---|---|---|
| `raw[i]` on a `[]int` | 197.5 ns | — |
| `ad[i]` on a `Slice[int]` — builtin syntax | 202.5 ns | +2.5% |
| `ad.At(i)` — through the accessor | **196.8 ns** | **±0%** |
| `vec.At(i)` — through a struct wrapper | 242.9 ns | **+23%** |

`Slice.At` costs nothing even as a method call, matching raw indexing, while the
struct wrapper `experiments/vectorcost` measured is 23% worse. The adapter's
accessor inlines to an index into the slice the loop bound came from, so the
check is still provable; the wrapper's indexes a field reached through a pointer,
and it is not.

A caveat on the evidence: `-gcflags='-d=ssa/check_bce/debug=1'` reports a
remaining check inside *both* accessors' method bodies, because an inlined body
keeps its original source position. It therefore does not separate the two. **The
timings do** — three groups, ±3%, consistent.

## 4. It gives the sized constructors a length — but see section 5

ADR `0015` made `Vector.Append` non-variadic, so bulk-appending a plain `[]T`
goes through either a length-carrying `Elems` or a bare iterator with none.

| append 1024 elements into an **empty** Vector | | allocs |
|---|---|---|
| `v.AppendAll(Slice[int](s))` | **2.375 µs** | **6** |
| `v.AppendAllSeq(slices.Values(s))` | 4.070 µs | 15 |
| raw presized `append(es, s...)` — the floor | 1.085 µs | 1 |

**1.71x and 6 allocations against 15.** The adapter supplies `Len`, so
`slices.Grow` allocates once where `append` regrows about eleven times.

The win is much smaller when the target is not empty:

| append 1024 onto a Vector already holding 1024 | | allocs |
|---|---|---|
| `v.AppendAll(Slice[int](s))` | 4.451 µs | 7 |
| `v.AppendAllSeq(slices.Values(s))` | 5.250 µs | 6 |

**1.18x, and one allocation *more*.** A vector with 1024 elements already has
capacity to absorb most of the growth, so `Grow`'s single large allocation
replaces only one or two doublings. Worth stating plainly: the headline figure is
the empty case, and the empty case is the one `Collect`-style construction hits.

## 5. Variadic expansion beats both, and the two forms are complementary

The question section 4 did not ask: what if the bulk method simply took `...T`?

| append 1024 into an **empty** Vector | | allocs |
|---|---|---|
| `v.AppendMany(s...)` — variadic | **1.124 µs** | **1** |
| raw `append(es, s...)` — the floor | 1.169 µs | 1 |
| `v.AppendAll(Slice[int](s))` | 2.409 µs | 6 |
| `v.AppendAllSeq(slices.Values(s))` | 4.266 µs | 15 |

**Variadic expansion is the floor.** It reaches `append`'s own variadic form,
which is one memmove with a known length — no iterator, no yield per element,
one allocation. It is 2.1x the adapter and 3.8x the bare iterator.

Non-empty: 3.796 µs / 2 allocs variadic against 4.818 µs / 7 for the adapter.

This is not the cost ADR `0015` measured. That was `Append(e T)` against
`Append(es ...T)` for **one** element, where the `...T` is paid per call. Here
the expansion happens once for the whole batch, so a separate variadic *bulk*
method costs the single-append path nothing.

### But `Elems` wins in the other direction

| append 1024 from another **container** | | allocs |
|---|---|---|
| `v.AppendAll(other)` — via `Elems` | **2.388 µs** | **5** |
| `v.AppendMany(slices.Collect(other.All())...)` | 4.518 µs | 13 |

A caller holding a container and offered only a variadic method has to
materialise a slice first: 1.9x and eight more allocations.

**So neither form subsumes the other**: variadic is optimal when the source is
already a slice, `Elems` when it is already a container. A container offering
both covers each at its floor.

The consequence for a slice adapter is direct and unflattering: **feeding a
plain `[]T` to a bulk append is not a reason to have one.** A variadic bulk
method does that job 2.1x faster than converting to an adapter.

## 6. A view over it must take a pointer

| construct a sequence view | | allocs |
|---|---|---|
| over a `*Vector` (one word) | 0.371 ns | 0 |
| over a `Slice` **by value** (three words) | **12.25 ns** | **1** |
| over a `*Slice` (one word) | 0.377 ns | 0 |

A slice header is three words, so a view holding one by value is not
pointer-shaped and boxes with an allocation — the same mechanism
`experiments/viewiface` measured. Holding `*Slice[T]` instead is free.

That is an awkward result for an adapter whose selling point is value semantics:
`ViewSlice(&s)` requires an addressable `Slice`, so it cannot be applied directly
to a function's return value. `Map` does not have this problem, because a map
header is one word.

## 7. The view does not need the adapter

A view can be taken over a plain `[]T` directly, holding `*[]T` — one word, so it
boxes free, exactly like a view over a `*Vector`:

| | construct | `At` | `All` sum of 1024 |
|---|---|---|---|
| over a bare `*[]int` | 0.375 ns | 1.10 ns | 1.150 µs |
| over a `*Slice[int]` | 0.370 ns | 1.05 ns | — |
| over a `*Vector[int]` | 0.375 ns | 0.98 ns | 1.144 µs |

Indistinguishable, all zero-allocation. The adapter contributes nothing.

```
view over a plain []T, taken before any append: Len=3 At(0)="a"
```

The view holds the address of the variable, so the owner's appends — including
the reallocating ones — are visible through it, and the field stays a `[]T`,
keeping `append`, `range`, indexing and `encoding/json`.

### And the adapter cannot serve the index/value case

```
Slice[string] does not implement Elems2[int, string] (wrong type for method All)
        have All() iter.Seq[string]
        want All() iter.Seq2[int, string]
```

A type has one `All`. `Slice`'s yields values, so it satisfies `Elems[T]` and not
`Elems2[int, T]`; `AllIndexed` is a different method under a different name.
Feeding index/value pairs into a dict-shaped constructor would need a *second*
adapter whose `All` yields pairs — which would then not satisfy `Elems[T]`.

## 8. It round-trips through `encoding/json`

```
json.Marshal: Slice -> [1,2,3]   Vector -> {}
json.Unmarshal into Slice: [4 5 6] err=<nil>
```

This is the one thing no struct-shaped container in this library can do, and it
is among ADR `0009`'s stated reasons for keeping `Map`. `Vector` marshals as `{}`
with a nil error, discarding its contents, exactly as every other container here
does.

## Conclusions

Durable:

1. A value receiver on a defined slice type can write an existing element but
   cannot change the length. A slice adapter is therefore read-and-write-in-place
   only, and cannot be the mutable equivalent of `Map`.
2. An adapter fixes none of the slice hazards `Vector` exists for. It is an
   ergonomic convenience, not a safety one.
3. A defined slice type keeps bounds-check elimination, through its accessor as
   well as through builtin syntax — matching raw indexing where a struct wrapper
   costs 23%.
4. Supplying `Len` to a sized bulk operation beats a bare iterator — 1.71x and
   6 allocations against 15 into an empty target, 1.18x into a populated one.
5. **A variadic bulk form beats both** when the source is already a slice: 1.124
   µs and one allocation, which is the raw `append` floor, against 2.409 µs and
   six for the adapter. It is not the per-call cost ADR 0015 measured, since the
   expansion happens once per batch. But `Elems` beats variadic by 1.9x when the
   source is a container, because the caller would otherwise have to materialise
   a slice. The two are complementary; neither subsumes the other.
6. A view over a slice adapter must hold `*Slice[T]`; by value it costs an
   allocation, because a slice header is three words where a map header is one.
7. A view over a plain `[]T` — holding `*[]T` — is indistinguishable from one
   over an adapter or over a `*Vector`, on construction, indexing and iteration,
   all allocation-free. **The adapter is not needed to give a slice a view.**
8. A slice adapter cannot serve the index/value case: a type has one `All`, and
   one yielding values satisfies `Elems[T]` rather than `Elems2[int, T]`.
9. A defined slice type round-trips through `encoding/json` — but so does a
   plain `[]T`, which is what it would be replacing.

Perishable: every absolute number above.
