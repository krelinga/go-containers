# What a defensive copy costs

Recorded from `bench.txt`, generated by `./run.sh` (`-count=10 -benchtime=200ms`).
Provenance is in the header of `bench.txt`; these numbers came from a **QEMU
guest**, which understates memory bandwidth. **Ratios are the durable result —
re-run on target hardware before citing an absolute.**

`benchstat` intervals below are ±% at 95% confidence.

## 1. Two regimes: an allocation floor, then bandwidth

`slices.Clone` of `[]int`:

| Elements | Time | Allocs | Throughput |
|---|---|---|---|
| 0 | 1.42 ns ± 2% | 0 | — (returns nil) |
| 1 | 9.77 ns ± 1% | 1 | 781 MiB/s |
| 8 | 16.93 ns ± 1% | 1 | 3.5 GiB/s |
| 64 | 80.12 ns ± 3% | 1 | 6.0 GiB/s |
| 512 | 587.7 ns ± 2% | 1 | 6.5 GiB/s |
| 4 096 | 2.985 µs ± 2% | 1 | 10.2 GiB/s |
| 65 536 | 30.49 µs ± 7% | 1 | 16.0 GiB/s |
| 1 048 576 | 305.6 µs ± 4% | 1 | 25.6 GiB/s |

Baseline `BenchmarkNoCopy` (return the header): **0.37 ns, 0 allocs**.

Roughly a **10 ns floor plus ~0.3–1 ns per 8-byte element**. Below a few
hundred elements you are paying for the allocation, not the copy.

## 2. A defensive copy is always a heap allocation

Identical 32-element input, three ways of expressing the copy:

| | Time | Allocs |
|---|---|---|
| `var c [32]int` (constant size) | 11.89 ns ± 5% | **0** |
| `make([]int, len(src))` | 40.64 ns ± 4% | 1 |
| `slices.Clone(src)` | 40.60 ns ± 8% | 1 |

`go build -gcflags=-m` reports `make([]int, len(src)) does not escape` for the
middle case — and it heap-allocates anyway. Not escaping only *permits* stack
allocation; the length must also be a **compile-time constant**, because the
compiler cannot reserve a frame of unknown size. `slices.Clone` never qualifies.

**Escape analysis will not make a defensive copy free.**

## 3. Retained pointers are re-charged on every GC cycle

Cost of one forced GC cycle with 200 000 elements held live:

| Retained | Cycle time | vs. nothing |
|---|---|---|
| nothing | 431.8 µs ± 1% | — |
| 200k pointer-**free** elements | 473.1 µs ± 1% | 1.10x |
| 200k pointer-**ful** elements | 1.042 ms ± 2% | **2.41x** |

Pointer-free copies are nearly invisible to the collector — spans with no
pointers are not scanned. Pointer-bearing copies are re-scanned on **every
cycle for as long as they are held**, so their cost is a subscription, not a
one-time charge. Element *width* matters far less than whether the element
contains pointers.

This ratio is sensitive to overall heap state; it measured 3.4x in an earlier
low-sample run. Treat the direction as solid and the magnitude as approximate.

## 4. Map clones are a different cost class from slice clones

At 65 536 entries:

| | Time | Allocs |
|---|---|---|
| `slices.Clone([]int)` | 30.49 µs ± 7% | **1** |
| `maps.Clone(map[int]int)` | 186.0 µs ± 5% | **258** |

**~6x the time and 258x the allocations.** There is no memmove available to a
map clone — it allocates buckets and rehashes. Any design that treats "copy the
slice" and "copy the map" as the same move is mispricing the map.

## 5. The failure mode that actually happens: copy-per-call

A caller indexing an accessor inside a loop — idiomatic, and it looks like O(1)
indexing at the call site:

| n | `Defensive()` | `View()` | Ratio |
|---|---|---|---|
| 64 | 5.026 µs ± 2% | 17.00 ns ± 2% | **296x** |
| 1 024 | 1.127 ms ± 6% | 275.5 ns ± 3% | **4 090x** |
| 16 384 | 160.6 ms ± 3% | 4.364 µs ± 1% | **36 800x** |

At n=16 384 the copying accessor allocated **2.1 GB** in one iteration.

An O(n) copy behind an accessor called n times is O(n²). Nothing about the
per-copy cost being ~10 ns prepares you for 160 ms.

## Conclusions

Durable (implementation facts, not machine facts):

1. A dynamic-length copy always heap-allocates, regardless of escape analysis.
2. Pointer-free retained data is not GC-scanned; pointer-ful data is, every cycle.
3. Map clone is ~6x slower per entry than slice clone and allocates per bucket.
4. A copying accessor hides an O(n) cost behind O(1)-looking syntax.

Perishable: every absolute number above.

**A single defensive copy of a small, pointer-free slice is genuinely free.**
The cost is not per-copy — it is in retention (2) and repetition (4). See
`docs/adr/0001-views-vs-defensive-copies.md` for what this decided.
