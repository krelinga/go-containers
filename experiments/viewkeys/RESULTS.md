# Converting keys through a view

From `bench.txt`, generated by `./run.sh` (`-count=8 -benchtime=100ms`).
Provenance in that file's header; a QEMU guest, so **ratios are the durable
result**. Zero-cost baseline `BenchmarkNoOp` = 0.4 ns.

## 1. The hole: `comparable` admits pointers

ADR 0011's views project values only. `K comparable` includes pointer types, so
`HashDict[*Item, string]` is legal and its view hands back the raw `*Item`,
which the holder mutates.

## 2. The payoff is larger than safety: the raw type leaves the API

| view | satisfies |
|---|---|
| value-only, over a `*Item` key | `Dict[*Item, ItemView]` |
| key-converting | `Dict[string, ItemView]` |

**The raw mutable type appears in the contract's own signature.** Anything
accepting a value-only view over a pointer key has `*Item` in its parameter list,
so the leak is not only what `All` yields — it is the API surface of every
function that takes one. Converting keys removes it entirely.

The same holds for sets, and it repairs something ADR 0011 recorded as lost:

| set view | satisfies |
|---|---|
| outbound only (`Has` takes `T`, `All` yields `NT`) | `Elems[NT]` only |
| both directions (`Has` takes `NT`, `All` yields `NT`) | **`Set[NT]`** |

ADR 0011 accepted that projecting set views satisfy `Elems[R]` but not `Set[R]`,
because the two halves disagreed about which type they spoke. Converting inbound
makes them agree.

## 3. Relaxing the contracts to `any` is free

`Set`, `Dict`, `MutableSet` and `MutableDict` constrain their key or element
parameter to `comparable`. A converted key need not be comparable, so the
contracts must relax for a converted view to satisfy them.

Changing all four to `any` and rebuilding the library: **it compiles and the
entire test suite passes with no other changes.** The constraint was never
load-bearing on the interface — only implementations need comparable keys, and
they declare that themselves.

## 4. What it costs

| | size | `Get` | iterate 1 024 |
|---|---|---|---|
| direct container call | — | 4.2 ns | — |
| value-only view | 16 B | 5.4 ns | 6 604 ns |
| key-converting view | **32 B** | **6.7 ns (+24%)** | 7 255 ns (+10%) |

Two more function fields, so the struct doubles. Both forms already allocate
when boxed as a contract, so that cost does not change — only the width does.

The per-access cost is the inbound conversion plus the outbound key conversion.
Iteration pays only the outbound one, hence the smaller +10%.

## 5. A failed inbound conversion is a miss

```
inbound conversion failure -> {<nil>}, ok=false
```

A converted key need not correspond to a real one, so the inbound direction
returns `(K, bool)`. A failure must read as "not present" rather than panicking
or producing a wrong answer, so that `Get` on a converted view behaves exactly
like `Get` on the container.

## Conclusions

Durable:

1. `comparable` admits pointers, so value-only views leak mutable keys.
2. The stronger argument is the API surface: a value-only view over a pointer key
   puts the raw type in the contract it satisfies, not merely in what it yields.
3. Converting both directions restores `Set[NT]` satisfaction for projecting set
   views, which ADR 0011 recorded as lost.
4. Relaxing the contracts from `comparable` to `any` compiles and passes with no
   other changes; the constraint was never needed at the interface.
5. Two-way conversion costs a doubled struct (16 to 32 bytes) and ~24% on a
   lookup, ~10% on iteration.

Perishable: every absolute number above.

## Not measured, and needing a decision

**Ordered operations assume the key conversion preserves order.** `Floor(NK)`,
`Ceil(NK)` and `Range(lo, hi NK)` convert their bounds inbound and then operate
in `K`'s order. If the conversion is not order-preserving, the result is a range
in `K` order presented as though it were in `NK` order. This is a semantic
hazard, not a performance one, and no benchmark surfaces it.
